topic: Multi-agent A2A architecture: Orchestrator, Research, and Voice agents
updated: 2026-08-23T21:10
---

- (capability) CAP-1 Orchestrator is the sole UI-facing agent; routes AG-UI requests deterministically into research / voice / research_and_voice / general, falling back to an LLM router only when rules cannot classify safely.
- (capability) CAP-2 Research Agent exposes an A2A endpoint and Agent Card, answers research questions via the existing RagPipeline, and returns sourced answers or a clear no-results response.
- (capability) CAP-3 Voice Agent exposes an A2A endpoint and Agent Card, drives the existing voice API and voice factory, and preserves the durable run-state model and human review step.
- (capability) CAP-4 Orchestrator can delegate to both specialists for one request and combine their results into a single response (the training-run diagnosis workflow is the reference case).
- (capability) CAP-5 Specialist failures are isolated: an unavailable Research Agent still leaves voice work usable, an unavailable Voice Agent still leaves research usable, and general requests still work if both are down.
- (capability) CAP-6 Orchestrator discovers specialist skills and capabilities from their published Agent Cards at a configured URL, never hard-coded in the router.
- (capability) CAP-7 Every delegated task is observable: agent name, skill, A2A task ID, context ID, target, and status are recorded in logs and traced through the existing Langfuse/OpenTelemetry pipeline.
- (capability) CAP-8 The network publishes its own ARD catalog and serves an ARD registry search API over it, so the agent set is a queryable resource and not private configuration. The official ARD conformance tool must pass on both.
- (constraint) Use the current released A2A specification and a pinned SDK version (https://a2a-protocol.org/latest/specification/). No custom JSON protocol may be presented as A2A.
- (constraint) Research Agent must not start or modify voice runs and must not call the voice factory.
- (constraint) Voice Agent must not query Qdrant or depend on RAG for normal voice operations; the two pipelines stay unmerged.
- (constraint) voice_runs.phase stays the state machine and VoiceRunReconciler stays its only writer; the Voice Agent wraps the existing reconciler, it does not replace or duplicate it.
- (constraint) MCP is not adopted in this first implementation.
- (constraint) No A2A push notifications in the first version.
- (constraint) Discovery follows the ARD specification and supersedes the earlier "no service-discovery infrastructure" constraint. This service is both an ARD publisher (static ai-catalog manifest) and an ARD registry (search API). A configured URL per specialist stays the transport fallback, so ARD being down degrades discovery but never breaks delegation.
- (constraint) ARD is a v0.9 draft with Proposal status; pin and record the targeted revision because the schema will change.
- (constraint) ARD trustManifest is out of scope: no SPIFFE, no attestations, no JWS signing. Identifiers use a placeholder publisher domain and the docs must say the trust binding is not real.
- (constraint) Orchestrator task records persist user request, decision, target agent, A2A task ID, task result, and final response only; never full agent reasoning or hidden chain-of-thought.
- (constraint) CI must not require a real GPU training job; the voice factory and GPU training are mocked in all automated tests.
- (constraint) Any new Postgres access uses SQLAlchemy 2.0 async only, per project-wide convention.
- (decision) Non-goal: a swarm of agents or an agent for every tool.
- (decision) Non-goal: agent-to-agent free-form conversation.
- (decision) Non-goal: a separate planner agent, reviewer agent, or memory agent.
- (decision) Non-goal: MCP adopted solely for demonstration.
- (decision) Non-goal: A2A push notifications.
- (decision) Non-goal: ARD federation across organizations. The registry answers for its own catalog, accepts the federation field and honours "none", but publishes no referrals and calls no upstream registry.
- (decision) Non-goal: ARD trust manifests, attestations, or signature verification.
- (decision) Non-goal: distributed consensus, agent self-replication, or automatic agent creation.
- (decision) Non-goal: real GPU model training in CI.
- (decision) Non-goal: merging the RAG pipeline into the voice pipeline, or adding RAG calls to voice operations without a concrete future need for it.
- (note) Success signal: ask the Orchestrator why a training run is slow; it must query the Voice Agent for run status and training data, query the Research Agent for troubleshooting docs, and return one combined, concise explanation. This is the reference proof that A2A adds real value here, not decoration.
- (assumption) Assumed the local dev topology in the source (orchestrator:8000, research-agent:8001, voice-agent:8002) is illustrative, not mandatory, since the source marks it SHOULD and says module names MAY differ.
- (assumption) Assumed unauthenticated internal A2A calls are acceptable for local development only; the source explicitly requires authenticated A2A in production configuration.
- (question) Which A2A SDK and protocol version will be pinned at implementation time? The source defers this decision to implementation time.
- (question) Where will the initial Research Agent documentation corpus live, and who authors the four seed documents (dataset-requirements, diarization, piper-training, troubleshooting)? The source gives a suggested path but says the exact location MAY differ.
- (question) Should the Research Agent and Voice Agent run in-process inside pythonapi or as separate processes for the first version? The source allows either and only requires separate processes if proving remote A2A communication needs it.
