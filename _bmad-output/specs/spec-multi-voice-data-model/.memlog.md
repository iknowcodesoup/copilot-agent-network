- (direction) User asked to convert the spec at specs/002-pythonapi-multi-voice-data-model/README.md into BMAD SPEC kernel format, full fidelity into companions.
- (direction) Depends on spec-video-scoped-ingestion: this spec's routes and phases sit behind the gateway contract that spec changes.
- (note) Current gaps, from pythonapi code review: VoiceRunRow (orm.py:71-127) is one flat row per video, no voices or speakers table, voice name only lives as JSON keys inside one run's speaker_map blob, nothing links two runs as same voice different video.
- (note) voice_pipeline_graph.py (lines 63-90) is one graph per video: DOWNLOADING to DIARIZING to AWAITING_REVIEW to COMMITTING to TRAINING to EXPORTING to READY. Training phases are hard-coded into the ingestion flow.
- (note) approve_run (routes/voice.py:244-281) in one call names speakers, commits their clips, and starts training - naming, committing, and training are atomic with no separation of concerns.
- (note) VoiceRunRepository (repositories/voice_runs.py) only CRUDs by run ID. No query groups runs by voice, no query answers all videos contributing to voice X.
- (capability) CAP-1 intent: a voice is a durable entity independent of any single video, so many videos can contribute clips to the same named voice over time. success: creating voice X, then committing contributions from two different videos, leaves voice X with two contributions and a training run that includes clips from both.
- (capability) CAP-2 intent: video ingestion state and voice training state are tracked separately, so reviewing one video's clips never implies starting training. success: voice_runs tracks only ingest_phase (DOWNLOADING/DIARIZING/AWAITING_REVIEW/COMMITTED); a run reaching COMMITTED does not by itself change any voice's training phase.
- (capability) CAP-3 intent: assigning a video's speakers to voices and committing that assignment are separate actions, so a person can propose assignments and hold them before they become durable contributions. success: POST /runs/{id}/assign records proposed assignments without changing ingest_phase; POST /runs/{id}/commit creates contributions and moves ingest_phase to COMMITTED only when called.
- (capability) CAP-4 intent: training can be triggered explicitly for a voice, or automatically on first contribution, independent of any one run's lifecycle. success: POST /voices/{id}/train starts the voice's training graph; the voice's phase moves TRAINING to EXPORTING to READY, tracked apart from any run's ingest_phase.
- (capability) CAP-5 intent: the repository layer can answer voice-centric queries - which videos contributed to a voice, and what a voice's contributions are - not just run-centric CRUD. success: a query lists all contributions for a given voice_id, joined to their source run_id and video_id.
- (constraint) voice_runs is trimmed, not dropped: it keeps only id, source_url, video_id, video_title, ingest_phase, speaker_map (JSONB). primary_character, phase (the COMMITTING/TRAINING/EXPORTING/READY values), checkpoint_path, and training-stage columns move to the new voices table.
- (constraint) voice_contributions rows are immutable after creation - an audit trail of (voice_id, run_id, video_id, speaker_label, clip_count, committed_at), never updated in place.
- (constraint) The ingest graph and the voice graph are split LangGraphs, not one graph with more nodes: one ingest graph per video (ingestion only), one voice graph per voice (TRAINING through READY), the voice graph triggered when a contribution commits.
- (constraint) SQLAlchemy-only, async, Base.metadata.create_all pattern for the new tables - matches project-wide convention, no raw SQL.
- (non-goal) This spec does not change the multi-character clip-merge logic. stage_youtube_commit in star-trek-voyicer already merges clips from multiple videos under one character; this spec only ensures pythonapi tracks that merge clearly, via the contributions table.
- (non-goal) This spec does not touch the frontend. UI changes to present voices and videos as separate views are owned by spec-videos-and-voices-views, which depends on this spec's new routes and tables.
- (non-goal) This spec does not change the video-scoped filesystem layout or the gateway routes; that is spec-video-scoped-ingestion, upstream of this one.
