- (direction) User asked to convert the spec at specs/005-copilotkit-hook-surface/README.md into BMAD SPEC kernel format, full fidelity into companions.
- (direction) Depends on spec-agui-tool-loop (no frontend hook works until the tool loop lands) and spec-videos-and-voices-views (the Phase 2 tool inventory is written against that spec's views, not today's single list).
- (note) The application exists to show AG-UI and the CopilotKit hooks, but uses one hook. useAgentContext in features/voices/voice_event_stream.tsx (line 188) hands the agent a run list. Nothing else. So the agent reads a summary and does nothing: it cannot see what the user sees, and it cannot do what the user does.
- (note) Scope note from source: specs 002 and 003 rewrite the action inventory - approve_run becomes assign, commit, and train, and new Videos/Voices views replace the single list. So this spec fixes the hook policy and plumbing now, and names the concrete tool inventory only after 003 lands.
- (capability) CAP-1 intent: read-only state the agent needs - which run is open, and which action is legal in each ingestion phase - is published into the prompt via useAgentContext, placed in the component that owns the data so a collapsed card publishes no context. success: asking the agent which run is open names the expanded one; collapsing every card means the agent no longer reports clip detail.
- (capability) CAP-2 intent: the agent can run a cheap, reversible browser action - expanding a run - proving the outbound tool loop end to end against spec-agui-tool-loop. success: asking the agent to open a different run causes that run's card to expand in the browser.
- (capability) CAP-3 intent: starter prompt suggestions are seeded from the runs currently on screen, so they stay relevant as the run list changes. success: suggestions shown to the user change when the set of runs on screen changes.
- (capability) CAP-4 intent: a visible run-status indicator shows the agent is working, sourced from useAgent. success: the sidebar header reflects the agent's run status (e.g. working vs idle) during an active run.
- (constraint) Every hook choice follows the fixed Need-to-Hook policy table (read-only state to useAgentContext, browser function the agent runs to useFrontendTool, agent-proposes-person-approves to useHumanInTheLoop, custom UI for a server-run tool to useRenderTool, starter prompts to useConfigureSuggestions, run status to useAgent). This policy is stable and does not change when spec-videos-and-voices-views lands. See hook-policy.md.
- (constraint) The v1 hooks useCopilotReadable and useCopilotAction do not exist in @copilotkit/react-core/v2 and must never be used. Every doc snippet found using them translates: useCopilotReadable to useAgentContext, useCopilotAction with a handler to useFrontendTool, useCopilotAction with renderAndWaitForResponse to useHumanInTheLoop.
- (constraint) Placement rule: useAgentContext lives in the component that owns the data, not in one central file, so the agent sees exactly what the screen shows and no more.
- (non-goal) The concrete Phase 2 tool inventory - classifying each Videos/Voices view action as useFrontendTool or useHumanInTheLoop - is deliberately out of scope for this pass. Writing it against today's approve_run would produce a spec that spec-videos-and-voices-views deletes. See Open Questions.
- (non-goal) This spec does not touch the pythonapi tool-call plumbing itself; that is spec-agui-tool-loop, which this spec depends on.
- (question) Open: once spec-videos-and-voices-views lands, what is the concrete tool inventory for the new Videos and Voices actions, classified by the policy table - which become useFrontendTool (reversible) and which become useHumanInTheLoop (costly or destructive, e.g. commit assignments, train, discard)?
