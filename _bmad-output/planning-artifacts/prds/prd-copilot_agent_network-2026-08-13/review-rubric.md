# PRD Quality Review — copilot_agent_network

## Overall verdict

This PRD is unusually disciplined on the mechanics the checklist rewards most — every one of its 27 FRs carries a verifiable condition, its Non-Goals/Assumptions/Open-Questions machinery is used at real tensions rather than as decoration, and its existing-code references check out against the project's own conventions. What it has not earned is the "one PRD" framing: the two build threads are bridged by a thesis broad enough to justify almost anything, and the MVP as scoped ships a frontend tool built against a UI that the same MVP's other thread replaces, without ever confirming the two survive contact with each other. A UJ↔FR cross-reference is also swapped in a way that would mislead downstream story generation about which capability realizes which journey. Both are concrete, fixable defects, not a sign the document needs a rewrite.

## Decision-readiness — adequate

Open Questions (§8) are genuinely open — each states a real unresolved choice with the live options named (e.g. OQ-2: "a programmatic move, or an accepted one-time re-ingest in development?"), not a rhetorical question answered in the next sentence. `[NOTE FOR PM]` callouts land at real tensions: the status-indicator-with-no-FR gap in §4.2, the directory-migration decision in §4.3, and the "revisit immediately, this is sequencing not descoping" flag in §6.2. Decisions are stated as decisions — FR-18's split of assign/commit into "two separate, explicit steps" and FR-21's "separate state machines" are not hedged as considerations.

What is thin: the PRD asserts what was chosen but rarely names what was given up. §4.4's description frames assign/commit splitting into two steps as pure improvement ("rather than one irreversible action") without acknowledging the added operator friction (an extra click, an extra state to track) that a two-step flow costs relative to the one-step flow it replaces. Similarly, §4.2's description frames the CopilotKit hook wiring as pure gain without naming the cost of maintaining two context surfaces (`useAgentContext` payload plus `useFrontendTool`) as the UI evolves.

### Findings
- **medium** Trade-offs framed as pure wins (§4.2, §4.4 descriptions) — "two separate, explicit steps rather than one irreversible action" and the CopilotKit hook rewiring are both described only in terms of what's gained, not what the added steps/surface cost the operator or maintainer. *Fix:* add one sentence per feature description naming the cost side of the trade, even briefly.
- **low** Title itself is an open decision — line 9, "*Working title — confirm.*" — a document meant to ground shared vocabulary ships with its own name unconfirmed. *Fix:* resolve before this PRD is cited by epics/stories, or move the caveat to Open Questions so it's tracked like the others.

## Substance over theater — strong

No findings. The JTBD framing in §2.1 substitutes for a personas section and stays lean (three roles, each driving at least one UJ) rather than padding out to generic personas that don't drive decisions. Feature-specific NFRs are concrete and product-specific — "All five gateway-bound routes... update in the same change... this is a hard breaking-change pairing, not two independent rollouts" (§4.3) and "The `voice_runs` table gains columns for this change and is dropped/recreated in development" (§4.4) — not the boilerplate "must be scalable/secure/reliable" the checklist warns about. The Vision statement (§1) risks boilerplate phrasing ("enterprise-grade," "not a toy chatbot") but is immediately grounded in specifics unique to this system (AG-UI, Qdrant+Postgres, LiteLLM, Langfuse, Piper TTS, lease-based mutual exclusion, replay-safe SSE) — it would not swap cleanly into another PRD in this category.

## Strategic coherence — thin

§0 states the PRD's own job plainly: it "grounds the two active build threads... in a shared vocabulary and a shared 'why'... instead of five independent spec kernels." That is an honest disclosure, but it also means the unifying thesis in §1 — both threads exist "to make the platform a more convincing, more complete showcase of production-grade agent engineering" — is a narrative applied after the fact to two specs that were written independently. That framing is broad enough to justify nearly any addition to this repo; it does not by itself establish that Thread 1 (agent tool loop) and Thread 2 (voice data model) belong in the same MVP together.

There is a real integration point between the threads — UJ-1 and UJ-2 both operate on the Voices dashboard, which is exactly the surface Thread 2 rebuilds — but the PRD does not follow that connection through to its consequence. FR-10's `useFrontendTool` ("expand a specified run," §4.2) is built and validated (via SM-1, §7) against the *current* single flat run-list UI. §4.5, scoped into the same MVP (§6.1), replaces that flat list with separate Videos and Voices views (FR-23, FR-24). §4.2's own Out of Scope note acknowledges the sequencing hazard for the *new* actions ("to avoid building against the `approve_run` action this PRD's other thread removes") but never addresses whether FR-10 itself — built against the UI that 4.5 is about to dismantle — still binds correctly, needs rework, or simply breaks once 4.5 ships within the same MVP. Since SM-1 is the PRD's primary success metric and explicitly depends on FR-10, this is not a cosmetic gap.

Counter-metrics are named for SM-1 (SM-C1) but not for SM-2 or SM-3, which the checklist calls out specifically ("Counter-metrics named when SMs exist").

### Findings
- **high** Unverified survival of FR-10 across the same-MVP UI rework (§4.2, §4.5, §6.1, §7) — FR-10's frontend tool is built and validated against the pre-4.5 flat run-list UI; 4.5 replaces that UI in the same MVP; nothing in the PRD confirms FR-10 continues to work, gets reworked, or is re-validated once 4.5 lands, even though SM-1 (the primary success metric) depends on it. *Fix:* add an `[ASSUMPTION]` or `[NOTE FOR PM]` addressing whether FR-10 needs rework post-4.5, or explicitly sequence SM-1's validation before 4.5 ships.
- **medium** Unifying thesis is asserted, not demonstrated (§0, §1) — "a more convincing, more complete showcase of production-grade agent engineering" is broad enough to cover nearly any feature; no shared user, mechanism, or metric ties the two threads beyond both living in the same repository. §0's own admission that this PRD unifies "five independent spec kernels" supports reading the threads as two portfolios bundled for reporting convenience rather than one product arc. *Fix:* either name the concrete integration point (the shared Voices dashboard) as the thesis, or split into two PRDs with an explicit sequencing note between them.
- **low** Counter-metrics incomplete (§7) — SM-C1 counterbalances SM-1 only; SM-2 (multi-video voice) and SM-3 (re-ingest cost) have none named. *Fix:* either add counter-metrics or note explicitly why none apply to those two.

## Done-ness clarity — strong

No findings of substance. Every FR across all five features carries a testable, verifiable condition folded directly into its statement — FR-2's event ordering "reassembled argument text exactly matching what the model sent," FR-12's "no download, transcribe, or diarize step," FR-26's three named, distinguishable actions (assign / commit / discard) with precise state effects. None of the checklist's hedge phrases ("handles X gracefully," "reasonable performance," "user-friendly") appear anywhere in the document. Feature-specific NFRs carry the same rigor rather than adjectives-only claims. This is the dimension the rubric says to be most unforgiving on, and it holds up.

## Scope honesty — strong

No findings of substance. §5 Non-Goals does real work — each of its five bullets is tied to a specific feature and a specific reason, not generic disclaimers. Both inline `[ASSUMPTION]` tags (§2.1 audience; FR-20 dual-trigger) round-trip cleanly to §9's index with no orphans either direction. `[NOTE FOR PM]` callouts land at genuinely deferred decisions (§4.2 status indicator, §4.3 directory migration, §6.2 sequencing-not-descoping), not safe checkpoints. De-scoping is proposed openly — §6.2 is explicit that Phase 2 tooling is deferred "to avoid building against the `approve_run` action this PRD's other thread removes," a reason, not a silent omission.

## Downstream usability — adequate

This PRD is explicitly chain-top — §0 states its purpose is to "give `bmad-create-epics-and-stories` a single source to work from" — so this dimension carries more weight than it would for a standalone document. The Glossary (§3) is thorough and terms are used consistently across FRs (`ingest_phase` as the field, "Ingest Phase" as the concept; "Voice Contribution" as the concept, `voice_contributions` as the table). FR numbering (FR-1–FR-27) and UJ numbering (UJ-1–UJ-4) are each contiguous with no gaps or duplicate IDs.

One cross-reference is concretely wrong. UJ-1 ("An evaluator asks the agent to open a specific run, and it does," §2.3) claims "Realizes FR-1 through FR-6, FR-11." But FR-10 — "The agent can expand a run on the user's behalf... Asking the agent to open a different run results in that run's card expanding in the browser" (§4.2) — is verbatim UJ-1's mechanism, and it is instead claimed by UJ-2's range ("Realizes FR-7 through FR-10," §2.3). FR-11 (starter suggestions tracking visible state), which UJ-1 claims instead, has no evident connection to "opening a run." SM-1 (§7) corroborates the correct grouping: it validates "FR-1, FR-2, FR-3, FR-7, FR-8, FR-10" as the set that realizes "ask the agent to act on the Voices dashboard (expand a run)" — i.e., FR-10 belongs with the open-a-run story, not the state-aware-answer story. A story-generation pass that trusts the UJ→FR trace as written would misattribute the "expand a run" capability.

### Findings
- **high** UJ-1/UJ-2 FR-range cross-reference swapped (§2.3) — UJ-1 lists "Realizes FR-1 through FR-6, FR-11" and UJ-2 lists "Realizes FR-7 through FR-10," but FR-10 (the expand-a-run tool) is UJ-1's mechanism and FR-11 (starter suggestions) belongs with neither story cleanly. SM-1 (§7) validates FR-10 alongside FR-1/2/3/7/8, confirming FR-10 belongs to UJ-1. *Fix:* UJ-1 → "Realizes FR-1 through FR-6, FR-10"; UJ-2 → "Realizes FR-7 through FR-9, FR-11" (or verify intended grouping directly with the source specs before correcting).

## Shape fit — strong

No findings. This is a brownfield, chain-top PRD covering a hybrid of UX-facing capability (the agent visibly acting on screen, which makes UJ-1/UJ-2 load-bearing rather than overhead — the entire point of Thread 1 is a live, observable UI interaction) and backend/data-model capability (4.3/4.4, appropriately treated as capability-spec FRs without forcing UJs onto pure schema and state-machine work). Existing-code references check out against the project's own documented conventions — the §4.4 NFR ("`voice_runs` table gains columns... dropped/recreated in development... no migration tooling") matches the project's CLAUDE.md almost verbatim, and the CopilotKit v2 hook policy table (§4.2 Notes) correctly bans the v1 hooks the project has already retired. Rigor is calibrated to real complexity (multi-service architecture, GPU pipeline, LangGraph) rather than over-formalized for its stakes.

## Mechanical notes

- **Section numbering gap**: "### 2.1 Jobs To Be Done" (line 23) is followed by "### 2.3 Key User Journeys" (line 30) — there is no "2.2." Cosmetic, but worth closing before this document is treated as a stable reference.
- **Assumptions Index roundtrip**: clean. Both inline `[ASSUMPTION]` tags (§2.1, FR-20/§4.4) appear in §9, and both §9 entries trace back to an inline tag. No orphans in either direction.
- **Scope-disclaimer convention**: per-feature omissions use bold **"Out of Scope:"** labels (§4.1, §4.5) rather than the checklist's suggested inline `[NON-GOAL for MVP]` tag. Functionally equivalent — each instance names a specific omission and a reason — just a different label than the checklist names; not a defect.
- **Testable-consequence formatting**: FR-1 alone carries an explicit "**Consequences (testable):**" subsection; every other FR (FR-2 through FR-27) folds its testable condition directly into the FR's own sentence instead. Content stays verifiable throughout — this is a presentation inconsistency, not a substance gap.
- **Required sections**: all present for this stakes level — frontmatter, Document Purpose, Vision, Target User (JTBD + UJs), Glossary, Features/FRs, Non-Goals, MVP Scope, Success Metrics, Open Questions, Assumptions Index. Nothing missing.
